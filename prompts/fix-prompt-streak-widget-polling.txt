## Bug — Streak widget polls every 5 seconds forever: visible re-render + repeated full Firebase reads

File: public/dashboard/scripts/streakWidget.js, initStreakWidget()
(around line 194): `setInterval(checkAndRender, 5000);`

checkAndRender() (defined just above it) runs, on every single tick,
forever, for as long as the dashboard stays open:

1. cleanupOldEntries() — cheap, localStorage only.
2. cleanupOldFirebaseEntries(callback) — defined in public/js/streakUtils.js.
   This does `reviewsRef.once('value', ...)` against
   `users/{uid}/Master/reviews`, i.e. a full read of the user's entire
   reviews node from Firebase Realtime Database, every single call. Its
   only purpose (per its own code) is to find and delete entries with a
   timestamp older than MIN_VALID_TIMESTAMP — a one-time data-migration
   concern, not something that needs re-checking every 5 seconds forever.
3. renderStreakWidget() — rebuilds the widget's HTML and swaps it in via
   `existingWidget.outerHTML = widgetHTML`, a full DOM replacement, on
   every tick regardless of whether the underlying data changed. This is
   the visible "streak view keeps refreshing" symptom.

The widget already has proper event-driven update paths further down in
the same file:
  document.addEventListener('suraRefreshed', function() {
    setTimeout(renderStreakWidget, 100);
  });
  window.addEventListener('languageChanged', function() { ... renderStreakWidget(); });
These correctly re-render only when something actually changed. The
5-second poll duplicates this with a blind timer, causing both the
unwanted visible refresh and a full Firebase reviews-node read every 5
seconds for the lifetime of the dashboard session — over an hour that's
720 redundant full reads of the same data.

Fix:

1. Remove the `setInterval(checkAndRender, 5000)` polling loop entirely.
   Rely on the existing event-driven re-renders (`suraRefreshed`,
   `languageChanged`) plus the one initial call already made via
   `checkAndRender()` right before the setInterval line (the
   `if (typeof get_local_storage_object === 'function') { checkAndRender(); }`
   block) for the initial render on load.

2. Separate the cleanup concern from the render concern — they don't
   belong on the same trigger. Run cleanupOldEntries() and
   cleanupOldFirebaseEntries() ONCE per app session (e.g. once from
   initApp() in init_app.js after auth confirms a signed-in user, or once
   from initStreakWidget() guarded by the existing
   `streakWidgetInitialized` flag so it can't repeat), not on any
   recurring timer. If there's a reason to re-check for new stale entries
   periodically (e.g. entries could still be written with bad timestamps
   after the initial cleanup), use a much longer interval appropriate to
   that reason (e.g. once per session, not every 5 seconds) — confirm
   with me which cadence is actually needed before picking one; don't
   default back to a short interval.

3. Double-check there's no other reason the widget currently depends on
   the 5-second tick to stay in sync (e.g. some other code path that
   mutates surasHistory without firing `suraRefreshed`). If you find one,
   report it before changing anything — the fix should be to make that
   path fire the event, not to keep the poll.

After the fix, confirm in a browser: open the dashboard, watch the Network
tab and the streak widget for a couple of minutes with no interaction —
there should be no recurring Firebase reads and no visible re-render of
the widget.
